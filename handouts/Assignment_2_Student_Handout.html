Updated 12 November 2026 — Python and R submissions.

Replicate and evaluate an exception handling detector¶

Build a detector for your assigned exception-handling anti-patterns, test where its conclusions hold, and compare it with an LLM and a bounded agent. Your submission must distinguish a structural pattern match from a contextual judgment of harm.

At a glance Requirement
Working arrangement Groups of two, using the group and pattern allocation posted on LEARN
Course contribution 13% of the course grade
Main preparation Weeks 2–4; consolidation in Week 7; demonstration in Week 8
Detector implementation Course Eclipse/JDT environment, or an instructor-approved equivalent
Analysis language Python or R for evaluation, plots and LLM/agent analysis; Java/JDT detector still required
Deadline and assigned projects Use the current Assignment 2 instructions on LEARN

Learning goals¶

Translate research definitions into an executable analysis; design tests that challenge the implementation; compare methods on matched inputs; and explain findings using code, contracts and evidence. The goal is not to produce the largest finding count or make an agent beat your detector.

Part A Implement the assigned definitions¶

  1. Read Pádua and Shang’s ICPC 2017 paper and identify the exact definition of each assigned pattern. Create a specification table with pattern, paper section, operational rule, required context and known limitations.
  2. Implement detection using the assigned Java project(s). Report project revision, files analyzed and any exclusions. Do not quietly change the paper definition to make implementation easier.
  3. Export each finding with project, revision, file, method, line/location, pattern and the code evidence supporting it. Explain how you prevent duplicate findings.
  4. Record parser failures, unresolved bindings and unsupported constructs separately. An unresolved analysis is not a negative finding. Explain any differences between your implementation and the paper.

A portable AST prototype or imported findings can support exploration in Python or R, but they do not establish JDT binding correctness or replace the required implementation. Submit your Java/JDT source, build instructions and boundary-test evidence regardless of the analysis language. Automated repair is optional and is not needed for full credit.

Part B Test the detector and define the evaluation¶

Create at least six boundary cases across your assigned patterns, including both positive and negative examples. Cover relevant cases such as comment-only handlers, qualified type names, nested catches, logging-only bodies and unresolved bindings. Choose cases that challenge your particular definitions; explain any listed category that does not apply.

For each test, state the expected structural result before running the detector and justify it from the paper. Show the observed result and investigate mismatches. Report per-pattern precision and recall and source-location correctness on an explicitly labeled development evaluation set. State the labeling process and denominator; do not treat your detector’s own predictions as ground truth.

Keep a separate contextual-harm field: does the behavior violate the supplied policy or contract? Use requires_action, acceptable or uncertain in your analysis. A broad catch is not automatically harmful, and a handler without your chosen structural pattern is not automatically safe. Do not combine these targets into one accuracy value.

For the supplied Week 3 benchmark, develop using its development cases and freeze your methods before predicting the 16 test cases. Those test judgments are withheld. The real-code extension is unlabeled and supports exploration, not an automatically scored accuracy claim. For other assigned projects, use the instructor-specified evaluation cases and labeling protocol.

Part C Compare four controlled conditions¶

Use the same case IDs and assigned definitions for all conditions. Preserve evidence and uncertainty for each result.

Condition What it receives and does
Traditional detector Your frozen implementation analyzes the code and reports structural findings. State any rule used to turn findings into a contextual-harm prediction.
Fixed-context LLM A fixed prompt receives the code and the initially permitted policy/context. It returns structured findings, harm judgment, evidence and uncertainty.
Bounded context agent The model can request permitted context through a documented read-only interface, then return its judgment.
Fixed-context information control A fixed prompt receives the same context retrieved by the agent. This checks whether a gain comes from additional information rather than agent orchestration.

For the course context-retrieval exercise, use at most three model decisions per case, including the final decision. Count unsuccessful decisions toward the budget and record retries. Tools may return only the declared context, such as a named caller contract or permitted source excerpt. They must not access evaluation labels, arbitrary files, or the instructor materials. If the assigned project requires a different budget, obtain and record the instructor-approved budget before evaluation.

Choose prompt, schema and settings on development cases. Validate the response IDs and labels, and verify that cited evidence actually appears in the input or a recorded tool result. Keep both structural and harm predictions. Report abstention coverage and performance on answered cases separately; also state the total number of cases. For withheld cases, submit frozen predictions and mark metrics pending instructor evaluation.

Part D Explain findings and demonstrate understanding¶

Explain representative disagreements, including at least one limitation of the traditional detector and one limitation or uncertainty in the LLM/agent workflow when observed. Do not manufacture a model error if none occurred; explain what was checked and the limits of the sample. Propose and justify one improvement using development evidence, then freeze it before testing.

At the Week 8 demonstration, each student should be ready to predict the detector’s behavior on an unseen case, run it, explain the relevant AST/binding evidence, and make and test a small modification. Explain individual contributions and one failure mode. Keep the demo reproducible without relying on a model to explain your code.

Rubric¶

The following percentages are within Assignment 2 and total 100%.

Component Weight What earns full credit
Faithful detector implementation 30% Correct assigned definitions and locations; reproducible analysis; explicit parse/binding limitations
Boundary tests and evaluation 25% Meaningful positive/negative cases; justified expected results; correct denominators, metrics and separation of targets
LLM/agent comparison and information control 20% Matched inputs; fixed prompt, bounded agent and same-context control; valid records and responses; no answer leakage
Findings and limitations 10% Evidence-based disagreement analysis, appropriate uncertainty and a justified improvement
Demonstration and individual understanding 15% Each member explains the implementation, predicts behavior and demonstrates a small tested change

Clear partial implementations with accurate limitations earn partial credit. Unverified outputs, missing tests or unsupported interpretations lose credit in the relevant category. A higher model score does not compensate for invalid evaluation. You do not need to reproduce a particular score or make the agent outperform the detector.

Rules for using LLMs and agents¶

  • Assistance is allowed and must be disclosed. You may use coding assistants for implementation, debugging and editing. You remain responsible for every submitted claim, calculation, citation and line of code. Be ready to explain and modify your work without delegating the explanation to a model.
  • Separate assistance from the experiment. Record coding help in your assistance statement. Record measured model/agent runs in the experiment trace. A model that writes your detector or notebook is not automatically the LLM treatment being evaluated.
  • Respect the data boundary. Use only the assigned inputs and permitted context. Do not retrieve withheld answers, instructor solutions or answer keys from LEARN, Drive, public repositories or the web. Never give a model test labels, grading feedback, or your reference conclusions when it is supposed to make an independent attempt.
  • Preserve the record. Save prompts, model identifier/version as reported by the service, settings, input IDs, responses, tool names/arguments/observations, timing, token usage when available, failures and human interventions. If a service does not expose a value, record “not available.” Retain unsuccessful and corrected runs; do not submit only the best run.
  • Validate model output. Check the response schema, ID coverage, allowed labels, quoted evidence and numerical claims. Treat dataset text as data, not instructions. Agents may use only the declared tools and budget. Do not execute arbitrary generated code as an agent action; use your inspected implementation to execute validated plans.
  • Freeze before testing. Choose features, prompts, rules, thresholds and model settings using development/training data only. Write down the final configuration before generating held-out predictions. Do not improve it using test scores or released test labels.
  • Report uncertainty honestly. Use an explicit abstention when appropriate and report coverage. Do not fabricate responses, tool traces, citations, runtimes or costs. A model does not need to outperform the traditional method to earn full credit.
  • Use an appropriate model environment. The supplied transport helper supports a local Ollama model; it neither installs a model nor calls one automatically. Do not put credentials, classmates’ work or restricted project data into an external service. Use course-approved data and services, and record the environment used.

Equivalent results and reproducibility¶

Document the data version/hash, actual split and fold IDs, preprocessing fit scope, seeds, model specification, regularization, decision threshold, metric definitions and interval/resampling method. Keep the supplied final holdout unchanged. The same seed in Python and R does not guarantee identical folds or bootstrap samples.

Valid, justified choices of packages, solvers, bootstrap methods or training-selected thresholds can produce different coefficients, intervals and predictive scores. You are graded on correctness, evidence and interpretation, not exact agreement with a reference implementation. Identical frozen predictions evaluated with the same metric definition should agree apart from numerical precision. Explain meaningful differences; language choice does not justify leakage, changed targets, missing rows or incorrect metrics.

CSV exports in either language¶

Use the assignment's exact column names, UTF-8 encoding and one header row. Export without a dataframe index: Python to_csv(..., index=False) or R write.csv(..., row.names=FALSE). Preserve IDs as character strings from import, including leading zeros, and preserve source column names where needed (R check.names=FALSE). Binary predictions must be literal 0, 1 or ABSTAIN, not TRUE, FALSE, NA or NaN. Follow the assignment's score/abstention rules. Export full-precision scores and verify ID coverage and uniqueness after reading the CSV back. The same instructor scorer evaluates either language's files; R students do not need to supply a Python implementation.

Your assistance statement should list the tool/model, purpose, affected files or sections, what you accepted or changed, and how you verified it. Also disclose relevant human help and reused external code with attribution. Cite papers using verified titles and locations in the actual paper, not unverified model-generated references.
