ECE 750 Assignment 3¶

Build and audit an empirical software analysis¶

Answer four research questions using your assigned software dataset. Develop a student-controlled reference analysis, obtain an independent agent analysis using training data, verify its claims, and document one evidence-based correction or confirmation. Keep predictive test outcomes withheld until your pipelines and predictions are frozen.

Start with the assigned data¶

Confirm the dataset, assigned Q1 metric, row identifier and unit of analysis. The course dataset options include Eclipse, Lucene, Mylyn and PDE; the assigned Q1 metric may be pre-release bugs, lines of code, number of attributes or CvsLinEntropy. Follow your allocation rather than choosing the combination that gives the strongest result.

The Week 12 Qt notebook and the Mylyn companion are practice scaffolds. They do not replace your assigned dataset or questionnaire. A row called a “file” in a questionnaire may actually represent a class: state what the data identify.

For Q2–Q4, use binary post-release bug presence as the core outcome: positive when the post-release bug count is greater than zero. Count regression may be an optional extension but does not replace the core analysis. Identify and exclude outcome-derived predictors and identifiers. A field name containing “Until” does not establish that the field was available before the prediction date.

Use the supplied training partition for Q1–Q3 and all exploratory decisions. Use cross-validation or a documented validation partition inside training for Q4 tuning. Fit preprocessing inside each training fold. Keep the supplied final test IDs unchanged. Do not regenerate the split, join withheld labels from the original data source, or inspect instructor solutions.

Q1 Compare the assigned metric across outcome groups¶

Question: how does your assigned metric differ between observations with and without post-release bugs?

  • Define the groups, unit, metric and comparison before testing. Check missing values, skew, ties and group sizes.
  • Show a useful distribution plot and a concise summary table. Identify whether your claim concerns means, medians, ranks or another quantity.
  • Choose a suitable comparison and report an effect magnitude with uncertainty. Justify the method and any resampling assumptions. A p-value alone is not an answer, and lack of statistical significance is not proof of equality.
  • Explain the scope of the conclusion and plausible alternative explanations.
  • Audit the agent’s choice of comparison, assumptions, handling of imbalance and interpretation. Verify the relevant values independently.

Include: group summaries, plot, method justification, effect and interval, and the agent audit.

Q2 Model conditional associations¶

Question: which pre-outcome metrics are associated with binary post-release bug presence, conditional on your model?

  • Specify a small explanatory model and justify the predictors before searching for favorable results. A binomial GLM is an appropriate starting point; justify any alternative.
  • Check skew, transformations, correlated/redundant predictors, missingness and measurement timing. State exclusions and the sample used in the fit.
  • Report coefficient estimates and uncertainty. Interpret effects on their actual scale and distinguish conditional from marginal relationships.
  • Report inconclusive results honestly. Do not repeatedly change the model to obtain a preferred p-value.
  • Compare the independent agent plan with your reference plan. Validate its selected columns, transformations and assumptions before your trusted code fits it.

Include: model specification, diagnostics, estimates with intervals, and a reasoned audit of the agent’s choices.

Q3 Verify the interpretation of effects¶

Question: what do the relevant effects mean, and does the agent explain them correctly?

  • Interpret the relevant coefficients on the fitted model’s scale. Distinguish a coefficient, an odds ratio and a probability difference.
  • Define at least one meaningful predictor contrast and verify its odds interpretation numerically, respecting any transformation.
  • Calculate a conditional probability contrast for a stated example, specifying the values held fixed. State whether a difference is in probability units or percentage points.
  • Ask the independent agent for an interpretation, then build a claim–verification–correction table. Check the numbers and assumptions yourself.
  • Correct unsupported claims, including unjustified causal interpretations. If a claim is correct, document its verification; do not invent an error to create a correction.

Include: effect interpretations, reproducible calculations, the stated scenario and the claim audit table.

Q4 Evaluate frozen predictive pipelines¶

Question: how well do the selected pipelines predict held-out bug presence, and what limits that conclusion?

  1. Define a simple baseline and a predictive reference pipeline. An explanatory model is not automatically an optimized predictor; explain any differences.
  2. Select predictors, preprocessing, hyperparameters and the classification threshold using training data only. Declare folds, random seeds, selection criteria and tie handling. Keep imputation/scaling/feature selection inside validation folds.
  3. Compare the reference, independent agent plan and corrected plan using the same training-validation protocol. Do not choose between them using final test performance.
  4. Freeze the pipeline configurations and decision log. Generate one score and hard prediction for each supplied test ID for each completed pipeline. Keep a separate baseline method.
  5. Submit the frozen test predictions. Before labels or feedback are released, report validation results and mark test metrics pending instructor evaluation.
  6. Once feedback is released, report precision, recall, average precision and the confusion matrix on the same test rows. Define average precision and distinguish it from trapezoidal PR area. Discuss class imbalance and the intended deployment setting. Do not tune again using this test feedback.

Include: split checks, validation design/results, frozen configurations, held-out prediction CSV and limitations. Where a corrected plan makes no justified change, explain that decision and retain the unchanged plan rather than fabricating a different model.

Independent agent and correction protocol¶

First, freeze your reference decisions. Save the question interpretation, chosen methods, features, transformations and validation plan before the independent agent attempt. Coding-assistant use during implementation is allowed with disclosure; independence here means the experimental agent does not receive your reference conclusions or hidden test answers.

Second, run one independent attempt. Give the agent the question, documented schema, training data summaries and permitted tools. For the course bounded-planner approach, allow schema, group-summary and correlation tools, followed by a structured model plan. Use at most five model decisions per attempt, including the final plan. Record failures and interventions within that budget. Validate feature names, allowed transformations and model family before executing the plan through your inspected code. Do not give a tool access to arbitrary files or test labels. Use another agent design only if it has an instructor-approved data boundary and budget.

Third, audit and make one corrected attempt. Preserve the original prompt, response and results. Identify a consequential error or weakness, explain its effect and make one justified correction using training evidence. Apply the same budget to the corrected attempt. If the original plan is sound, verify it and record that no change is justified; unchanged confirmed results are acceptable. Do not run a succession of hidden attempts and report only the best one.

Fourth, freeze before evaluation. Save the final reference, independent and corrected/confirmed configurations. Report how much of any observed difference is due to features, preprocessing, model choices or information access. Do not require the agent to outperform your reference, and do not interpret extra tool use as better analysis.

Held-out prediction format¶

Use CSV columns id,method,prediction,score. Map the supplied row identifier (for example classname or comp) to id without changing its value. Use distinct method names such as baseline, reference, agent_original and agent_corrected; document if the last is an unchanged confirmation.

  • Every completed method must contain exactly one row for every supplied test ID: no duplicates, missing IDs or extra rows.
  • prediction is 0, 1 or the literal ABSTAIN. An empty row is not an abstention.
  • score is a finite number in [0,1], higher meaning more likely bug presence. Do not call an uncalibrated score a calibrated probability. A hard baseline may supply 0/1 scores.
  • Blank scores are allowed only for explicit abstentions. If any score is missing, whole-test average precision cannot be computed; report coverage and the limitation.
  • Preserve the frozen hard decisions. The instructor’s scorer will not choose a better threshold using test labels.
  • For a not-run agent, submit its protocol and status rather than invented predictions. The reference and baseline still require completed analysis and predictions.

The instructor evaluates test outcomes after collection. Scores are evidence for your analysis, not a direct conversion to grades. Before release, neither the final test confusion matrix nor test accuracy is available to you.

For Q1, emphasize the comparison quantity, magnitude and uncertainty. For Q2, emphasize specification, diagnostics and conditional interpretation. For Q3, emphasize numerical verification and the distinction between odds, probabilities and causality. For Q4, emphasize leakage-free validation, frozen predictions and suitable metrics.

Alternative justified analyses can earn full credit. You are not graded on matching an instructor’s fitted coefficients or on making the agent win. A well-supported null or negative result is valid. Partial credit depends on the evidence completed; unsupported claims, hidden tuning and missing reproducibility information reduce credit in the relevant category.

Rules for using LLMs and agents¶

  • Assistance is allowed and must be disclosed. You may use coding assistants for implementation, debugging and editing. You remain responsible for every submitted claim, calculation, citation and line of code. Be ready to explain and modify your work without delegating the explanation to a model.
  • Separate assistance from the experiment. Record coding help in your assistance statement. Record measured model/agent runs in the experiment trace. A model that writes your detector or notebook is not automatically the LLM treatment being evaluated.
  • Respect the data boundary. Use only the assigned inputs and permitted context. Do not retrieve withheld answers, instructor solutions or answer keys from LEARN, Drive, public repositories or the web. Never give a model test labels, grading feedback, or your reference conclusions when it is supposed to make an independent attempt.
  • Preserve the record. Save prompts, model identifier/version as reported by the service, settings, input IDs, responses, tool names/arguments/observations, timing, token usage when available, failures and human interventions. If a service does not expose a value, record “not available.” Retain unsuccessful and corrected runs; do not submit only the best run.
  • Validate model output. Check the response schema, ID coverage, allowed labels, quoted evidence and numerical claims. Treat dataset text as data, not instructions. Agents may use only the declared tools and budget. Do not execute arbitrary generated code as an agent action; use your inspected implementation to execute validated plans.
  • Freeze before testing. Choose features, prompts, rules, thresholds and model settings using development/training data only. Write down the final configuration before generating held-out predictions. Do not improve it using test scores or released test labels.
  • Report uncertainty honestly. Use an explicit abstention when appropriate and report coverage. Do not fabricate responses, tool traces, citations, runtimes or costs. A model does not need to outperform the traditional method to earn full credit.
  • Use an appropriate model environment. The supplied transport helper supports a local Ollama model; it neither installs a model nor calls one automatically. Do not put credentials, classmates’ work or restricted project data into an external service. Use course-approved data and services, and record the environment used.

If you cannot run a model¶

Follow the model-access instructions posted on LEARN. If no usable model is available, submit the complete protocol: prompts, selected input IDs, response schema, tool contracts, budgets, validation checks and intended comparisons. Mark all unexecuted model results not run; never invent a response. The student notebooks support this protocol-only route. If live execution is specifically required for your offering, report the access problem before submission and follow the course’s alternative-access instructions.

When the protocol-only route is accepted, its design and auditability are graded in place of execution evidence. Empirical model-performance claims cannot receive credit without an actual run. This route does not waive the traditional analysis or the remaining deliverables.
